# **Viability Assessment of Alternative SLAM, TSDF, and 3D Reconstruction Frameworks for Sparse dToF LiDAR \+ IMU Handheld Scanner**

## **1\. System Architecture and Baseline Bottleneck Analysis**

The development of the "lidar-roomscanner"—a tethered, handheld 3D scanning device—introduces a confluence of algorithmic and computational challenges. The hardware architecture streams timestamped telemetry from an STM32H563ZI microcontroller over a native USB CDC or UDP Unicast transport layer. The primary spatial sensor is an STMicroelectronics VL53L9CX Direct Time-of-Flight (dToF) imager operating at 30 to 46 Hz, yielding a highly sparse ![][image1] resolution matrix (2,268 spatial points per frame) alongside an 8-bit infrared (IR) intensity grid. Kinematic state estimation is driven by an ST X-NUCLEO-IKS4A1 sensor suite, which provides hardware-fused Sensor Fusion Low Power (SFLP) orientation quaternions at 30 Hz. The host computational environment is a Linux-based Python 3.11 asynchronous backend leveraging an NVIDIA RTX 2000 Ada (16GB VRAM) to drive a FastAPI web server and Three.js frontend.  
The current baseline software architecture relies on the Open3D 0.19 Tensor API, utilizing its VoxelBlockGrid for Truncated Signed Distance Field (TSDF) integration, point-to-plane Iterative Closest Point (ICP) for odometry, and CUDA-based Marching Cubes for mesh extraction. While functional in controlled prototypes, this architecture exhibits severe limitations when deployed in expansive indoor environments.

### **1.1 The Sparse Planar Degeneracy Problem**

The fundamental limitation of the VL53L9CX sensor is its extreme sparsity. Traditional mechanical scanning LiDARs generate between 60,000 and 120,000 points per frame. The 2,268 points generated by the dToF imager provide insufficient geometric constraints when scanning environments dominated by planar surfaces, such as featureless interior walls. In optimization terms, the Fisher Information Matrix of the point-to-plane ICP algorithm becomes rank-deficient along the unconstrained axes of the plane. Without highly distinct geometric primitives (e.g., corners or dense furniture clusters), the point cloud lacks the longitudinal gradient required to anchor the optimization. This results in "sliding" degeneracies, where the ICP algorithm incorrectly converges on a translation vector that glides along the wall surface. To mitigate this, the SLAM optimization must tightly couple the external IMU SFLP quaternions as an absolute rotational prior, reducing the state estimation problem from a 6-Degree-of-Freedom (6-DoF) optimization to a strictly constrained 3-DoF translational solve.

### **1.2 Open3D Memory Constraints and GIL Starvation**

The Open3D VoxelBlockGrid relies on a pre-allocated spatial hashing mechanism. In large-scale continuous scanning scenarios (e.g., \~100 m² spaces at 10 mm voxel resolutions), the allocation of active voxel blocks frequently exceeds a hard operational ceiling of approximately 260,000 blocks, culminating in catastrophic host process segmentation faults.  
Furthermore, integrating real-time computer vision processing within a Python asyncio event loop requires meticulous thread concurrency management. The Python Global Interpreter Lock (GIL) enforces single-threaded execution of Python bytecode. When the Open3D C++ backend executes CUDA Marching Cubes and serializes the resulting geometry to the host CPU, it acts as a synchronous, CPU-bound blocking call. Because the legacy Open3D bindings do not systematically release the GIL (Py\_BEGIN\_ALLOW\_THREADS) during these heavy device-to-host memory transfers, the entire Python asyncio event loop is starved of execution time1. This starvation halts the FastAPI web server, triggering telemetry buffer overflows and causing the frontend interface to lock up entirely.  
The following sections present a deep-dive evaluation of alternative real-time tracking engines, volumetric meshing frameworks, and offline photogrammetry pipelines to resolve these systemic bottlenecks.

## **3\. Category A: Real-Time Tracking & Alignment Engines**

The odometry frontend must process the incoming 46 Hz dToF stream within a strict 21.7-millisecond latency budget, seamlessly ingesting the 8-bit IR intensity channel and adhering to the 30 Hz IMU rotational priors.

### **3.1 small\_gicp (Adopt)**

Developed by Kenji Koide, small\_gicp is a highly optimized, header-only C++ library that implements parallelized Generalized Iterative Closest Point (GICP) and Voxelized GICP (VGICP) algorithms3. It is specifically engineered to eliminate the threading overhead found in legacy libraries like the Point Cloud Library (PCL), offering highly scalable performance on both multi-core CPUs and CUDA backends5.  
**Sparse Point Cloud Handling:** Unlike point-to-plane ICP, which relies on discrete surface normal estimation, GICP models local point neighborhoods as continuous Gaussian distributions, minimizing a distribution-to-distribution metric5. This probabilistic approach is significantly more resilient to the high noise and extreme sparsity of the 2,268-point VL53L9CX output. The framework employs highly parallelized KdTree and Linear iVox (incremental voxel) structures for nearest-neighbor searches5. To succeed with point counts below 5,000, the algorithm's adaptive voxelization must be carefully parameterized; specifically, the downsampling\_resolution must be set to a minimal value or entirely disabled to prevent the eradication of the already sparse geometry prior to alignment3.  
**Rotational Prior Integration & 3-DoF Solving:** The framework’s modular architecture, built heavily on C++ templates, allows granular control over the Gauss-Newton and Levenberg-Marquardt optimization variables4. SFLP quaternions can be injected directly as the initial rotation guess matrix ![][image2]. Crucially, small\_gicp permits explicit masking of the state space. By applying a rotation mask of 0, the optimizer is strictly forbidden from altering the rotational variables, forcefully anchoring the optimization to the IMU's absolute orientation6. This transforms the GICP algorithm into a constrained 3-DoF translation solver, entirely circumventing the rotational drift associated with planar degeneracies.  
**IR Intensity Feature Fusion:** The modular cost function in small\_gicp allows the augmentation of the standard geometric covariance matrices. The 8-bit IR intensity gradients from the dToF sensor can be ingested as a photometric channel alongside the spatial coordinates7. This creates an intensity-augmented correspondence search7. In geometrically featureless corridors, varying IR reflectance (e.g., from doors, posters, or varying paint finishes) yields sharp photometric gradients. By binding the geometry to the intensity, the algorithm anchors the translational drift along the previously unconstrained plane.  
**Performance & Language Bindings:** small\_gicp natively provides Python bindings distributed via the Python Package Index (PyPI) and supports modern dependency structures3. Its execution latency is industry-leading. Benchmarks on equivalent sparse point clouds (\~4,700 points) demonstrate single-frame execution times of approximately 3.2 milliseconds on standard multi-threaded CPUs10. When processing 2,268 points, the execution latency falls well below 2 milliseconds, consuming less than 10% of the 21.7 ms budget required for 46 Hz operation.

### **3.2 KISS-ICP (Pass)**

Developed by the Photogrammetry and Robotics Lab at the University of Bonn, KISS-ICP (Keep It Small and Simple) advocates for a minimalist approach, relying on point-to-point ICP fortified with robust kernels, spatial downsampling, and an adaptive correspondence thresholding mechanism11.  
**Sparse Point Cloud Handling:** The fundamental architecture of KISS-ICP is intrinsically hostile to extreme sparsity. The pipeline was explicitly engineered for dense 64-beam and 128-beam mechanical automotive LiDARs13. The algorithm relies on building a semi-dense local map representation on-the-fly via aggressive voxelized downsampling14. When applied to sparse sensors (e.g., 32-beam architectures), the developers explicitly state that the system "typically does not perform well out-of-the-box" because the aggressive downsampling destroys the minimal geometry required for the adaptive thresholding to function14. Processing a 2,268-point frame through this pipeline leaves virtually no points for the algorithm to align, resulting in immediate tracking failure.  
**Rotational Prior Integration & IR Fusion:** KISS-ICP explicitly challenges the necessity of IMU integration, relying instead on a constant velocity motion model for scan deskewing and initial guesses11. While highly effective for smooth automotive trajectories, this model immediately breaks under the erratic, high-acceleration kinematics of a human-operated handheld scanner. There is no native API hook to inject strict SFLP IMU quaternions or restrict the solver to a 3-DoF translation constraint. Furthermore, the framework does not natively support IR intensity as a strict constraint within the optimization loop11.

### **3.3 GTSAM (Adopt)**

The Georgia Tech Smoothing and Mapping (GTSAM) library is the premier C++ framework for sensor fusion, formulating the SLAM problem as a probabilistic factor graph optimization15.  
**Factor Graph Potential & Real-Time Feasibility:** Constructing a real-time multi-sensor factor graph is highly feasible using GTSAM. The framework utilizes the iSAM2 (Incremental Smoothing and Mapping) algorithm, which relies on a dynamic Bayes tree data structure to identify and update only the specific variable cliques affected by new measurements16. This avoids full batch recalculations, enabling the backend to seamlessly process dToF ICP pose steps, IMU pre-integration, and auxiliary barometer/magnetometer telemetry at rates well above the 46 Hz hardware limit17.  
**Rotational Prior Integration & 3-DoF Solving:** GTSAM is mathematically designed to ingest external priors with exact covariance tuning. The 30 Hz SFLP quaternions can be injected into the graph using Pose3AttitudeFactor or PriorFactor\<Pose3\> nodes19. To enforce a strict 3-DoF constraint, the rotational covariance of the prior noise model can be driven to a near-zero value (e.g., ![][image3]), while the translational covariance is left loosely bounded21. The iSAM2 optimizer will probabilistically treat the IMU's absolute rotational constraints as an unyielding anchor, forcing the graph to absorb all residual error into the translational axes. Furthermore, GTSAM's PreintegratedImuMeasurements class allows for the exact mathematical integration of raw IMU linear accelerations between dToF frames, maintaining strict kinematic fidelity22.

## **4\. Category B: Alternative Real-Time Volumetric TSDF & Meshing Engines**

The local mapping backend is responsible for integrating the optimized poses from the SLAM frontend with the raw depth scans into a unified volumetric representation, facilitating the real-time extraction of polygonal meshes for the web interface.

### **4.1 nvblox (Adopt)**

Developed by NVIDIA, nvblox is a modern, GPU-accelerated library specifically designed for Truncated Signed Distance Field (TSDF) and Euclidean Signed Distance Field (ESDF) generation24.  
**Standalone Usability:** While heavily marketed within the Isaac ROS ecosystem, nvblox is fundamentally structured as a standalone C++ library26. It features independent CMake configurations, allowing it to be compiled and linked directly into a custom Python/C++ backend without pulling in the massive overhead of ROS 2 or Isaac Sim26.  
**Memory Limits & Scalability:** nvblox completely bypasses the static pre-allocation limitations that cause Open3D to crash at 260,000 blocks. It utilizes an advanced spatial hashing scheme paired with dynamic block allocation and aggressive recycling27. The system employs a voxel-centric integration architecture running entirely on the GPU; blocks are dynamically allocated via compare-and-swap (CAS) operations in a hash table27. Unseen or redundant blocks can be aggressively recycled or streamed out of active VRAM25. This allows the memory allocation to scale seamlessly across multi-room \~100 m² indoor environments without segmentation faults.  
**Mesh Extraction Latency & Zero-Copy GPU Interop:** Because the entire pipeline—from depth map raycasting to TSDF fusion and Marching Cubes—operates natively on the GPU, mesh extraction latency is restricted to single-digit milliseconds25. Crucially, nvblox resolves the GIL starvation bottleneck. By wrapping the C++ API with Pybind11, developers can explicitly invoke py::gil\_scoped\_release prior to launching the CUDA meshing kernels. This releases the Python interpreter, allowing the FastAPI asyncio event loop to continue serving web traffic concurrently1.  
Once the mesh is extracted, nvblox supports zero-copy memory export. The resulting CUDA device pointers for the vertex and face arrays can be wrapped using the \_\_cuda\_array\_interface\_\_ or DLPack protocols28. These pointers are ingested directly by PyTorch or CuPy arrays within Python, completely bypassing the CPU and eliminating the serialization overhead that plagues the current Open3D implementation28.

### **4.2 VDBFusion / OpenVDB (Benchmark/Fallback)**

VDBFusion is a robust TSDF integration library built upon OpenVDB, the Academy-Award-winning hierarchical data structure developed for high-resolution sparse volumes30.  
**Memory Limits & Scalability:** The underlying B+ tree topology of OpenVDB is arguably the most memory-efficient structure available for representing vast, unbounded 3D spaces31. It imposes virtually no topological restrictions on sparsity, managing massive scales (well beyond 100 m²) with minimal memory overhead31.  
**Mesh Extraction Latency & Zero-Copy GPU Interop:** While OpenVDB is historically a CPU-bound architecture, modern extensions such as NanoVDB and fVDB allow the tree structure to be transferred to the GPU for accelerated processing32. However, the core execution cycle of VDBFusion still involves compressing the sensor input on the GPU via NanoVDB, shuttling the data back across the PCIe bus to the CPU, and updating the global OpenVDB grid32. This required CPU-GPU memory transfer introduces a processing bottleneck. Extracting the mesh via Extended Marching Cubes (EMC) on the CPU can introduce latency spikes that violate the strict 30 Hz real-time requirements34. While Python integration is highly accessible via the standard vdbfusion pip package32, the inherent CPU-bound nature of the final mesh extraction prevents the true zero-copy, GPU-native DLPack interoperability offered by nvblox.

## **5\. Category C: Offline Detailed Mesh & Photorealistic Reconstruction**

The offline processing pipeline is tasked with generating high-fidelity, scale-accurate CAD surfaces (.ply/.obj) from the recorded 4K RGB video, leveraging the sparse dToF depth maps as geometric regularization priors.

### **5.1 SuGaR (Surface-Aligned 3D Gaussian Splatting) (Adopt)**

SuGaR represents a critical advancement in offline photogrammetry by introducing a regularization loss term to traditional 3D Gaussian Splatting (3DGS). This term forces the semi-transparent 3D ellipsoids to flatten and align with the underlying physical surface normals36.  
**ToF Depth Ingestion & COLMAP Bypassing:** Standard 3DGS pipelines rely heavily on COLMAP Structure-from-Motion (SfM) to deduce camera poses, a process that is highly computationally expensive and prone to failure in textureless indoor rooms. SuGaR bypasses this entirely by natively ingesting a transforms.json file containing pre-computed metric 6-DoF camera poses39. The optimized trajectory exported from the GTSAM engine can be formatted into this JSON, dictating the exact spatial scale and orientation for every 4K video frame. Furthermore, the accumulated sparse dToF point cloud can be injected as the initialization seed, anchoring the scale-accurate geometry from the first iteration.  
**Explicit Mesh Quality:** While traditional 3DGS produces clouds of disconnected splats unsuitable for architectural CAD software36, SuGaR actively extracts explicit meshes. It accomplishes this by sampling points across the aligned Gaussians and executing a Poisson Surface Reconstruction37. Poisson reconstruction yields globally closed, watertight surfaces. A known limitation of Poisson extraction in specular or unconstrained regions is the hallucination of "floaters" or artifact geometry42. SuGaR addresses this via the extract\_mesh.py utility, which includes a \--project\_mesh\_on\_surface\_points flag. This command reprojects the extracted Poisson vertices directly back onto the dense Gaussian centers, significantly sharpening planar walls and mitigating the floater artifacts45.  
**Training Time & VRAM:** Processing a 2-minute 4K video (approximately 3,600 frames, though downsampled to 300–500 keyframes for efficiency) is memory intensive. On an NVIDIA RTX 2000 Ada with 16GB of VRAM, the primary 3DGS training phase fits comfortably when utilizing gradient accumulation and moderate Gaussian density limits. However, the subsequent Poisson mesh extraction phase can cause VRAM spikes at high octree depths. Executing the mesh projection chunk-by-chunk mitigates out-of-memory errors, allowing the entire pipeline to resolve successfully within the 16GB boundary45.

### **5.2 Nerfstudio / Splatfacto (Benchmark)**

Nerfstudio is an expansive, modular framework that houses multiple volumetric rendering architectures, notably the Splatfacto and depth-nerfstudio pipelines39.  
**ToF Depth Ingestion & COLMAP Bypassing:** Similar to SuGaR, Nerfstudio is designed to seamlessly accept external SLAM trajectories via the transforms.json format, completely skipping COLMAP39. The Splatfacto pipeline specifically excels at utilizing sparse depth priors. By invoking the ns-train command with depth supervision flags, the model incorporates the sparse dToF measurements into its loss function39. This forces the Gaussians to initialize and optimize precisely at the measured spatial coordinates, drastically reducing training time and eliminating the geometric ambiguity commonly seen in purely RGB-driven 3DGS39.  
**Explicit Mesh Quality:** While Splatfacto achieves unparalleled photorealism for novel view synthesis, its architectural focus is volumetric. It does not inherently execute Poisson or Marching Cubes extractions to yield closed, scale-accurate polygonal meshes (.ply/.obj). Converting a radiance field into a clean CAD surface requires secondary workflows—such as rendering dense depth maps from the field and fusing them into a TSDF—which invariably introduces smoothing errors and geometric degradation compared to SuGaR's dedicated surface alignment mechanics. Therefore, Nerfstudio is highly viable for photorealistic rendering but suboptimal for explicit CAD extraction.

## **6\. Recommended Hybrid Architecture: The 2026 Stack**

Based on the forensic evaluation of the provided frameworks, the legacy Open3D Tensor API architecture must be deprecated. Its inherent susceptibility to GIL starvation, combined with pre-allocated memory ceilings and poor planar tracking under extreme sparsity, makes it mathematically and structurally unfit for the VL53L9CX hardware profile.  
The recommended optimal stack for the 2026 production software leverages a hybrid architecture, routing the frontend odometry, backend graph optimization, GPU-native meshing, and offline photogrammetry to their most capable respective engines.

### **Phase 1: Real-Time Frontend Odometry (small\_gicp)**

The incoming 46 Hz dToF telemetry and SFLP quaternions are ingested by the small\_gicp C++ frontend via Pybind11. The 2,268-point spatial data is combined with the 8-bit IR reflectance to formulate an intensity-augmented covariance matrix7. The Levenberg-Marquardt optimizer is configured with a strict zero-mask on the rotational state variables, locking the orientation strictly to the IMU SFLP prior6. The optimizer rapidly converges on the 3-DoF translation vector (![][image4]) without sliding along planar degeneracies. Utilizing OpenMP acceleration, this process completes in under 2 milliseconds per frame10, leaving the vast majority of the CPU available.

### **Phase 2: Backend Global Optimization (GTSAM)**

The sequential 3-DoF translation vectors and SFLP quaternions are passed to the GTSAM factor graph. PriorFactor\<Pose3\> nodes anchor the origin to ensure global scale and gravitational alignment19. High-rate raw linear accelerations from the LSM6DSV16X IMU are accumulated directly into PreintegratedImuMeasurements factors to maintain strict kinematic continuity between frames22. Operating asynchronously in a background thread, the iSAM2 solver continually updates the Bayes tree, optimizing the global trajectory and issuing high-precision pose corrections back to the frontend.

### **Phase 3: GPU-Native Volumetric Meshing (nvblox)**

The optimized 6-DoF poses and raw dToF point clouds are routed directly into the GPU via CUDA streams to the nvblox standalone C++ library26. nvblox updates its TSDF utilizing dynamic voxel hashing and block recycling, easily scaling to map multi-room environments without encountering the 260,000-block ceiling25. During TSDF fusion and Marching Cubes extraction, the Pybind11 wrapper explicitly releases the Python GIL (py::gil\_scoped\_release), ensuring the FastAPI server remains fully responsive to web client requests1. The extracted geometry is exposed to Python via the \_\_cuda\_array\_interface\_\_ protocol as zero-copy DLPack tensors, allowing instantaneous WebGL buffer streaming without CPU serialization overhead28.

### **Phase 4: Offline Photorealistic CAD Generation (SuGaR)**

Upon completion of the real-time scanning session, the system exports the globally optimized GTSAM trajectory to a standard transforms.json file39. For offline processing, SuGaR ingests this file alongside the 4K RGB video frames and the accumulated sparse dToF point clouds, entirely circumventing COLMAP SfM39. SuGaR optimizes the 3D Gaussian Splatting scene, utilizing its regularization loss to force the ellipsoids flat against the architectural surfaces36. Finally, the extract\_mesh.py script is executed with the \--project\_mesh\_on\_surface\_points flag, extracting a clean, globally closed, watertight Poisson surface mesh (.obj) that is free of hallucinated floaters and ready for professional CAD deployment41.

## **7\. Technical Implementation Details & Integration Architecture**

### **7.1 small\_gicp PyPI Wheel vs. Custom C++ Extension**
The standard pre-built PyPI wheel for `small_gicp` exposes Python bindings for basic spatial point cloud registration. Setting explicit optimization masks (such as a translation and rotation mask) is a feature supported in the core C++ optimizer API. However, `small_gicp` achieves its high performance by heavily relying on C++ templates to customize point cloud traits, correspondence estimators, and cost functions at compile time. Because these templates cannot be dynamically instantiated in Python, integrating an 8-bit IR intensity channel directly into the covariance calculation requires authoring a custom C++ structure. Therefore, the production system must compile `small_gicp` from source and author a custom Pybind11 wrapper to expose specific intensity-augmented template instantiations and strict 3-DoF solver masks to Python.

### **7.2 nvblox Standalone Python Integration & Build Recipe**
`nvblox` is designed to be built as a standalone C++ library using CMake without requiring ROS 2 or Isaac Sim. The core dependencies required to compile it independently include CUDA, Eigen, and glog (with gtest for unit testing). While there are community implementations that wrap the standalone CMake build into Pybind11 modules, the official repository focuses mostly on the C++ and ROS interfaces. To export GPU memory directly to the Python FastAPI backend without locking the event loop, authoring a custom Pybind11 bridge is required to securely expose the internal `nvblox` vertex and face device pointers via the `__cuda_array_interface__` or DLPack protocols.

### **7.3 Tracking Topology (small\_gicp + nvblox)**
The mapping topology must be decoupled entirely. `small_gicp` is engineered to maintain its own highly efficient internal map representations. It is strongly recommended to run `small_gicp` as a scan-to-model odometry frontend using its internal `Linear iVox` (incremental voxel) or Gaussian voxelmap structures. `Linear iVox` utilizes an LRU-cache-based voxel deletion mechanism to handle incremental spatial bounds efficiently. Attempting to extract a submap surface mesh or point cloud from `nvblox` and transferring it back to `small_gicp` for frame-to-model registration would introduce severe memory transfer overhead and synchronization latency, immediately violating the real-time budget.

### **7.4 GTSAM Python API Latency at 46 Hz**
While `GTSAM` offers robust Python bindings that wrap the underlying C++ `iSAM2` and `PreintegratedImuMeasurements` routines, relying on Python to construct factors and update the graph at 46 Hz introduces latency risks for a strict 3–5 ms latency budget. The cross-language serialization (passing objects through Pybind11 every 21 milliseconds) and the overhead of the Python Global Interpreter Lock (GIL) can introduce jitter, particularly when the FastAPI server is concurrently handling high-volume web traffic. To guarantee stable latency, executing the `iSAM2` factor graph thread entirely in native C++ is required. The system can then expose a minimal, non-blocking Python API purely for reading the latest optimized trajectory to feed `nvblox` and the web UI.

### **7.5 SuGaR Extrinsic Camera Rig Calibration**
Standard `transforms.json` files do not have a distinct field for raw sensor extrinsics; they expect the final $4 \times 4$ camera-to-world transformation matrix for every frame. The offline pipeline must apply the rigid hand-eye calibration matrix mathematically before generating the JSON. If `GTSAM` outputs the trajectory of the LiDAR origin in the world frame ($T_{\text{world\_lidar}}$), and the hand-eye calibration defines the camera's optical center relative to the LiDAR ($T_{\text{lidar\_camera}}$), the camera pose for each frame is calculated as:

$$T_{\text{world\_camera}} = T_{\text{world\_lidar}} \times T_{\text{lidar\_camera}}$$

This resulting $T_{\text{world\_camera}}$ matrix is written into the `transform_matrix` array for each frame. The camera's intrinsic parameters (e.g., `fl_x`, `fl_y`, `cx`, `cy`) are defined as standard top-level JSON keys alongside these pre-transformed poses.

## **8\. Production Architecture Specifications (roomscan-native)**

### **8.1 Unified Native C++ Core Engine (`roomscan-native`)**
Building a unified C++ shared library or daemon is the optimal architectural decision. Relying on Python to shuttle data between `small_gicp`, `GTSAM`, and `nvblox` at 46 Hz introduces cross-language serialization overhead and exposes the pipeline to Python GIL contention. By encapsulating UDP/CDC sensor ingestion, `small_gicp` odometry, the `GTSAM` iSAM2 factor graph thread, and `nvblox` CUDA calls within a single C++ memory space, the system guarantees deterministic execution well within the < 5 ms budget. The Pybind11 layer acts strictly as a read-only interface, exposing the optimized trajectory and zero-copy DLPack / `__cuda_array_interface__` mesh pointers to the Python FastAPI event loop for web UI rendering.

### **8.2 Loop Closure Detection in the GTSAM Graph**
`small_gicp` generates loop-closure constraints for the `GTSAM` backend using a submap-based approach (analogous to the GLIM SLAM architecture). As the operator maps a room, historical voxelmap or `Linear iVox` submaps are saved. When revisiting an area, the system searches for historical submaps near the current pose estimate and uses Voxelized GICP (VGICP) to compute the exact relative transformation. If a valid match with a high overlap score is found, that relative transformation is injected into the `GTSAM` factor graph as a loop-closure edge. To ensure scalability during multi-room scans (5–10 minutes), a keyframe sampling strategy filters down candidate pairs before executing VGICP matches.

### **8.3 VRAM Memory Pruning in nvblox**
While `nvblox` dynamically allocates voxel blocks only where spatial geometry exists, it does not automatically decay or evict blocks out of VRAM purely based on sensor distance. Left unmanaged during a 10-minute scan, the active voxel hash map will grow until VRAM is exhausted. To maintain a flat VRAM footprint, the C++ core manages a sliding window. The system periodically invokes spatial pruning logic via the `nvblox` C++ API to clear or serialize voxel blocks that fall outside a defined spatial radius around the sensor's current pose. For the offline `SuGaR` pipeline, evicted mesh blocks are streamed back to host CPU RAM or disk rather than permanently deleted.
