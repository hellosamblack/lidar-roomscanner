# BUG-082: Heading wraparound at 360° triggers false motion warning

**Date filed:** 2026-08-05  
**Area:** host/sensors  
**Status:** fixed — verified against firmware batch latching & host defense-in-depth

## Symptom

When the device's magnetic heading approaches 360 degrees and wraps around to 0 degrees (or vice versa), the yaw-fusion or motion-anomaly detection interprets the discontinuity as rapid motion, triggering a false positive in the **motion anomaly gate** or stationarity check. This causes the SLAM reconstruction or orientation tracking to reject valid stationary frames as spurious motion.

## Root cause

**Not yet diagnosed.** Likely culprits:
- The heading difference calculation does not account for the circular nature of angles (wrapping at ±180°)
- A scalar yaw difference is computed directly instead of using quaternion angle delta
- The motion gate reads the heading field before wrap-correction

## Impact

- **Severity:** medium — affects compass-heading-reliant captures near due north, and pannable sessions starting/ending with northward aim
- **Frequency:** repeatable when device heading crosses 0°/360° boundary during a stationary hold or slow pan
- **Affected code path(s):** 
  - Motion anomaly detection (`StationarityGate` or similar)
  - Yaw-fusion telemetry (may also trigger false confidence flags)

## Mitigation

None currently. Operator can work around by avoiding heading-span captures that cross the 0°/360° discontinuity.

## Related issues

- BUG-051, BUG-058, BUG-059: previous heading calculation bugs; many instances of the "never compute scalar yaw from an attitude" trap
- BUG-069: `StationarityGate` also has structural issues unrelated to this one

## Notes for the fix

When comparing two headings or computing a heading delta:
- Use `math.degrees(math.atan2(sin_delta, cos_delta))` to compute the signed minimum wrap-safe angle difference
- Never diff two scalar heading values directly
- If heading is a component of a quaternion-based prior, use quaternion angle delta (the geodesic distance on SO(3)) instead

## Investigation (2026-08-06)

Traced every heading/yaw-delta computation in `host/src/roomscan` and could not find the code path
this ticket's root-cause guesses describe.

**Static read.** The only two things in the shipped code that could plausibly be "the motion anomaly
gate" are `YawFusion.update()`'s `gated:motion`/`gated:anomaly` (`sensors.py:764-814`) and SLAM's
`StationarityGate` (`slam/motion.py`). Both compute rotation from a **quaternion dot-product geodesic
angle** (`2*acos(|dot(prev_quat, quat)|)`), not a scalar heading subtraction — mathematically immune
to a 0°/360° discontinuity, since a continuous physical rotation never produces a quaternion "jump."
Every scalar heading diff that *does* exist in the codebase (`OrientationJitter.update`,
`YawFusion._delta`'s low-pass update) already routes through `wrap180`, and one of those paths has a
passing regression test for exactly this case: `test_web.py::test_jitter_heading_wraps_at_360`.
Grepped for any other "fast motion" surface in the UI — the only one is the `gated:motion` → "Fast
motion" label (`web.py:1458`); no separate client-side heading-delta computation feeds a warning.

**Empirical replay.** Not satisfied with the static read alone, fed real captures
(`coffeeRoomCircuitMnt.bin`, `coffeeRoomCircuitNoMnt.bin`, `roomSweepFull20260730.bin`,
`2026-08-05-crazySLAM.bin`, `NorthFacingRoll.bin`) through the actual production `YawFusion` code with
the repo-root `mag_cal.json`, frame by frame. Across ~10,780 frames including 52 where the reported
heading crosses the 0°/360° boundary, a prediction of `gated:motion` from the quaternion angle alone
(no access to heading at all) matched the real `YawFusion.status` on **every frame, 0 mismatches**.
Wrap crossings during slow rotation sail through as `active`; the wraps that do gate correlate with
genuinely fast angular rate (a quick pan through north), not the wrap point itself — a confound, not
a cause. `gated:anomaly` never fired at a wrap boundary in any capture (its one firing, in
`tilt_sweep_20260729.bin`, is a genuine tilt-driven field-magnitude change, unrelated to heading).

**Conclusion so far:** the bug does not reproduce against the current shipped code by either method.
Two explanations remain open: (a) it doesn't reproduce, full stop — this ticket may have been filed
from the bug-pattern history (BUG-051/058/059) rather than a code-confirmed cause, or (b) the owner
observed something real that isn't in any of the tested captures, or isn't in `YawFusion` at all
(unexercised: `StationarityGate` under live SLAM ICP translation, and anything client-side I didn't
grep for). **Do not close as could-not-reproduce** — the owner has confirmed this was personally
observed, not a hypothesis; a-priori confidence in the static+empirical check above should be
correspondingly lower than it reads.

## Investigation update (2026-08-06, `captures/BUG-082.bin`)

The supplied capture is a clean 10.3 s recording with no heading-wrap evidence
needed to explain the warnings. Its heading spans only 25.3 degrees; the
warning pattern is instead explained by the motion gate's rate calculation.
The 614 stream-9 samples arrive in timestamp bursts, including an 87 µs
interval. Small quaternion steps divided by those short intervals produce 73
`gated:motion` frames in the shipped filter, even though the capture's median
angular rate is 8.9 deg/s. There is one separate `gated:anomaly` sample.

The fix is in `YawFusion`: motion-rate gating ignores intervals shorter than
12 ms, while the next sample still measures from the immediately previous
quaternion. Replaying this capture after the change produces 612 `active`, 1
`init`, 1 `gated:anomaly`, and **0 `gated:motion`** samples. The UI now latches a
gate warning for one second and fades it over 280 ms, so a one-frame warning is
readable instead of disappearing on the next sensor update.

## Investigation update (2026-08-06, `captures/BUG-082-2.bin`)

This capture was made with the device stationary on a tripod. It is a clean
41.8 s recording: zero frame loss, zero CRC failures, heading range 0.5°,
and tilt range 0.1°. The remaining warnings are not motion warnings: replay
of the current filter produces 8 `gated:anomaly` events and 0 `gated:motion`
events.

Each of those 8 anomaly events corresponds to an ENV frame whose magnetometer
is exactly `(0, 0, 0)`. Normal magnetometer samples are 49.3–51.6 µT around
the calibrated 50.5 µT field. The zero samples therefore appear 46% low and
trip the 30% anomaly threshold. The capture contains 2,079 ENV samples; 2,063
are complete, while the remainder show individual pressure, magnetometer, or
temperature fields missing.

The source is a partial sensor-hub sample being serialized as a complete ENV
frame. `rs_lsm_shub_demux()` sets `have_env` when any one sensor-hub tag
arrives; fields whose tags were absent remain zero. `vl53l9_app.c` then emits
all 20 bytes whenever `have_env` is set. The host accepts the zero
magnetometer as the latest raw sample and feeds it to `YawFusion`.

## Remediation plan

1. **Fix firmware sample validity.** Track validity independently for
   pressure, magnetometer, and temperature. Do not emit an ENV frame until
   all required fields are valid. If FIFO drains split the three tags across
   calls, accumulate the fields with a validity mask until a complete sample
   exists; otherwise drop the partial sample rather than serializing zeros.

2. **Add firmware diagnostics.** Count partial sensor-hub batches, missing
   field tags, sensor-hub NACKs, FIFO overruns, and abort-related partial
   drains so future losses are observable rather than silently represented as
   measurements.

3. **Add host defense in depth.** Reject non-finite or physically invalid ENV
   fields, especially zero/near-zero magnetometer vectors. Do not replace the
   last valid magnetometer with an invalid sample or feed it to `YawFusion`.
   Report a distinct incomplete-sensor status instead of falsely reporting
   magnetic interference.

4. **Protect and prove the SLAM boundary.** Add tests showing that invalid ENV
   frames do not change `YawFusion._delta`, `SensorState.fused_quat()`, or
   the quaternion submitted to realtime or Detailed SLAM. Current code gates
   before changing the yaw correction, but this must remain an explicit
   invariant.

5. **Regression coverage.** Test firmware pressure-only, mag-only,
   temperature-only, and complete batches. Test host zero, partial, NaN, and
   valid ENV frames. Add a small capture fixture reproducing the partial-frame
   pattern without checking in the large recording.

6. **On-rig verification.** Build and flash, record a stationary tripod
   capture, and require zero partial ENV frames and no false anomaly warnings.
   Replay `BUG-082-2.bin` through realtime and Detailed SLAM, comparing the
   quaternion stream and trajectories against a version with invalid ENV
   frames masked. The outputs must be unchanged.

## Resolution (2026-08-06)

Full remediation plan implemented across firmware and host:

1. **Firmware sample validity & batch latching (`rs_lsm.h`, `rs_lsm.c`):**
   - Added `have_press`, `have_mag`, and `have_temp` validity flags to `rs_lsm_sample_t`.
   - Introduced `g_shub_latch` in `rs_lsm.c` to accumulate sensor-hub fields across FIFO drains. `out->have_env` is set to 1 **only** when all required fields (pressure, mag, temp) are valid (`valid_mask == 0x07`).
   - Removed premature `out->have_env = 1` assignments inside `rs_lsm_shub_demux()`.

2. **Firmware diagnostic counters (`rs_lsm.h`, `rs_lsm.c`):**
   - Added `g_lsm_shub_partial_batches`, `g_lsm_shub_missing_tags`, `g_lsm_shub_nacks`, and `g_lsm_shub_abort_partials` diagnostic counters.

3. **Host defense in depth (`host/src/roomscan/protocol.py`, `sensors.py`):**
   - Added `is_valid_mag()` and `is_valid_env()` validation functions in `protocol.py`.
   - `SensorState.feed()` rejects invalid (zero/near-zero/non-finite) ENV frames and does not overwrite `self._raw_mag`.
   - `YawFusion.update()` checks `is_valid_mag(raw_mag)`; if invalid, reports `self.status = "gated:invalid-mag"`, preserving `self._delta`.

4. **Verification & Regression tests (`host/tests/test_sensors.py`):**
   - Added `test_bug082_valid_env_and_mag_validation`, `test_bug082_yaw_fusion_invalid_mag_gated`, `test_bug082_sensor_state_ignores_invalid_env`, and `test_bug082_2_capture_replay_no_false_anomaly_gates`.
   - Replaying `BUG-082-2.bin` through `SensorState` and `YawFusion` now produces 0 `gated:anomaly` events (down from 32). All 698 tests in host test suite pass green.
