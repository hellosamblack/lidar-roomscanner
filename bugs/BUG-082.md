# BUG-082: Heading wraparound at 360° triggers false motion warning

**Date filed:** 2026-08-05  
**Area:** host/sensors  
**Status:** blocked — awaiting a repro capture from the owner (personally observed, not yet
reproduced against the code)

## Symptom

When the device's magnetic heading approaches 360 degrees and wraps around to 0 degrees (or vice versa), the yaw-fusion or motion-anomaly detection interprets the discontinuity as rapid motion, triggering a false positive in the **motion anomaly gate** or stationarity check. This causes the SLAM reconstruction or orientation tracking to reject valid stationary frames as spurious motion.

## Root cause

**Not yet diagnosed.** Likely culprits:
- The heading difference calculation does not account for the circular nature of angles (wrapping at ±180°)
- A scalar yaw difference is computed directly instead of using quaternion angle delta
- The motion gate reads the heading field before wrap-correction

## Impact

- **Severity:** medium — affects compass-heading-reliant captures near due north, and pannable sessions starting/ending with northward aim
- **Frequency:** repeatable when device heading crosses 0°/360° boundary during a stationary hold or slow pan
- **Affected code path(s):** 
  - Motion anomaly detection (`StationarityGate` or similar)
  - Yaw-fusion telemetry (may also trigger false confidence flags)

## Mitigation

None currently. Operator can work around by avoiding heading-span captures that cross the 0°/360° discontinuity.

## Related issues

- BUG-051, BUG-058, BUG-059: previous heading calculation bugs; many instances of the "never compute scalar yaw from an attitude" trap
- BUG-069: `StationarityGate` also has structural issues unrelated to this one

## Notes for the fix

When comparing two headings or computing a heading delta:
- Use `math.degrees(math.atan2(sin_delta, cos_delta))` to compute the signed minimum wrap-safe angle difference
- Never diff two scalar heading values directly
- If heading is a component of a quaternion-based prior, use quaternion angle delta (the geodesic distance on SO(3)) instead

## Investigation (2026-08-06)

Traced every heading/yaw-delta computation in `host/src/roomscan` and could not find the code path
this ticket's root-cause guesses describe.

**Static read.** The only two things in the shipped code that could plausibly be "the motion anomaly
gate" are `YawFusion.update()`'s `gated:motion`/`gated:anomaly` (`sensors.py:764-814`) and SLAM's
`StationarityGate` (`slam/motion.py`). Both compute rotation from a **quaternion dot-product geodesic
angle** (`2*acos(|dot(prev_quat, quat)|)`), not a scalar heading subtraction — mathematically immune
to a 0°/360° discontinuity, since a continuous physical rotation never produces a quaternion "jump."
Every scalar heading diff that *does* exist in the codebase (`OrientationJitter.update`,
`YawFusion._delta`'s low-pass update) already routes through `wrap180`, and one of those paths has a
passing regression test for exactly this case: `test_web.py::test_jitter_heading_wraps_at_360`.
Grepped for any other "fast motion" surface in the UI — the only one is the `gated:motion` → "Fast
motion" label (`web.py:1458`); no separate client-side heading-delta computation feeds a warning.

**Empirical replay.** Not satisfied with the static read alone, fed real captures
(`coffeeRoomCircuitMnt.bin`, `coffeeRoomCircuitNoMnt.bin`, `roomSweepFull20260730.bin`,
`2026-08-05-crazySLAM.bin`, `NorthFacingRoll.bin`) through the actual production `YawFusion` code with
the repo-root `mag_cal.json`, frame by frame. Across ~10,780 frames including 52 where the reported
heading crosses the 0°/360° boundary, a prediction of `gated:motion` from the quaternion angle alone
(no access to heading at all) matched the real `YawFusion.status` on **every frame, 0 mismatches**.
Wrap crossings during slow rotation sail through as `active`; the wraps that do gate correlate with
genuinely fast angular rate (a quick pan through north), not the wrap point itself — a confound, not
a cause. `gated:anomaly` never fired at a wrap boundary in any capture (its one firing, in
`tilt_sweep_20260729.bin`, is a genuine tilt-driven field-magnitude change, unrelated to heading).

**Conclusion so far:** the bug does not reproduce against the current shipped code by either method.
Two explanations remain open: (a) it doesn't reproduce, full stop — this ticket may have been filed
from the bug-pattern history (BUG-051/058/059) rather than a code-confirmed cause, or (b) the owner
observed something real that isn't in any of the tested captures, or isn't in `YawFusion` at all
(unexercised: `StationarityGate` under live SLAM ICP translation, and anything client-side I didn't
grep for). **Do not close as could-not-reproduce** — the owner has confirmed this was personally
observed, not a hypothesis; a-priori confidence in the static+empirical check above should be
correspondingly lower than it reads.
