## BUG-080 — Web event log renders TX_QUEUE_STATS (EVENT code 7) as mojibake (fixed)

**Status:** fixed (2026-08-05) · **Area:** host/web (`reader.py` / `protocol.py` / `control.py` /
`viewer.py`) · **Found by:** owner, garbled bottom event-log lines on the live rig.

The bottom event-log console showed lines like `code=7 detail=131589 ��B=` for every firmware
TX-pacer telemetry ping. `reader.py` (the web log path), `viewer.py` and `control.py` all decoded
**every** EVENT frame through `parse_event()`, which ascii/`"replace"`-decodes the payload past
code+detail. That is correct for codes 1–6 (an ASCII message) but **wrong for code 7
`TX_QUEUE_STATS`**, whose payload there is three packed binary `u32` counters
(`enqueue_drops`/`stack_stalls`/`emitted_bytes`) — `protocol.py` even warned "Deliberately NOT
routed through parse_event()", but the live log did exactly that. The trailing "broken characters"
were the monotonically-growing `emitted_bytes` counter; the `detail` bitfield (high_water /
transport / pending) was legible but unlabelled. Nothing was wrong with the device — the telemetry
was healthy (transport=udp, 0 drops, 0 stalls) the whole time.

**Fix:** new `protocol.describe_event(payload) -> (code, detail, message)`, a display-layer superset
of `parse_event()` that names every code (`TRIGGER_TIMEOUT`, `AUTO_WAKE_MOTION`, …) and decodes
code 7's binary counters into `transport=… high_water=… pending=… drops=… stalls=… emitted=<IEC>`.
Routed into the three human-facing sites; `parse_event()` stays the low-level raw decode for
golden-vector tests. Verified live: the log now reads `code=7 detail=66055 TX_QUEUE_STATS
transport=udp high_water=7 pending=1 drops=0 stalls=0 emitted=1.30 GiB`. Same commit folded the
separate `#diag-card` diagnostics pane into this one console and added the top-bar comm-status
indicator (`commstatus.py`, `/ws` `comm` message) — see `docs/web-protocol.md`.
