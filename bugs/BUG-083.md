# BUG-083: Firmware emits `pressure = 0.0 Pa` on isolated ENV frames (baro dropout fabricates SLAM vertical)

**Date filed:** 2026-08-06
**Area:** firmware/scanner-stream (host mitigated)
**Status:** fixed (by BUG-082)

## Symptom

On isolated frames the ENV stream (stream 10) carries barometer `pressure` = exactly
`0.0 Pa` while every neighbouring frame is a sane ~98570 Pa. In
`captures/2026-08-05-crazySLAM.bin`, 4 of 1349 frames (312, 523, 944, 1270) were 0.0 Pa.

Downstream this was catastrophic for SLAM: `baro_height_m(0, ref)` returns the
formula ceiling of **44330 m**, and through the mapper's 0.05-authority / τ=900 baro
low-pass each single dropout injected a **+2.45 m vertical step**. The 4 dropouts
fabricated the capture's entire **8.6 m of phantom vertical "translation"** (ensemble:
path 18.0 m, closure 8.71 m) — reported at high ICP fitness with 0 tracking-lost, so
it read as real motion. The operator's actual movement was smooth.

## Root cause

`have_env` is decoupled from pressure validity. In `firmware/scanner-stream/Src/rs_lsm.c`
the ENV "have data" flag `out->have_env = 1` is set **independently by each** of the
three sensor-hub slaves — SLAVE0 pressure (`rs_lsm.c:393`), SLAVE1 mag (`:409`),
SLAVE2 temp (`:421`). But `pressure_pa` is only written when a pressure word was
actually drained: `if (shub_acc.press_n != 0) out->pressure_pa = ...` (`rs_lsm.c:738-741`).

The LPS22DF runs at 25 Hz (`rs_lsm.c:290`) while the sensor hub cycles at 60 Hz and the
FIFO is drained at the ToF rate (~28–30 Hz), so a given drain can contain a mag/temp
word but **no** pressure word. In that drain `have_env=1`, `press_n=0`, and
`pressure_pa` keeps its zero-init value (`rs_lsm_sample_t lsm = { 0 };`,
`vl53l9_app.c:666`). The emit site trusts `have_env` for the whole 20-byte payload and
ships `0.0`:

```c
// firmware/scanner-stream/Src/vl53l9_app.c:679-685
if (lsm.have_env) {
    memcpy(env + 0, &lsm.pressure_pa, 4);   // <-- 0.0 when press_n was 0 this drain
    ...
    rs_send_frame_cdc(RS_STREAM_ENV, seq, 0u, env, RS_ENV_SIZE, 0u, 0u);
}
```

There is **no** validity/DRDY/plausibility gate on pressure before packing
(`rs_lsm_shub_status_raw()` exists at `rs_lsm.c:549` but is only read by the bench probe).
A secondary path exists too: a raw 24-bit value of 0 from an incomplete SHUB conversion
would pass straight through `pa = raw * 100/4096` (`rs_lsm.c:386`) with no range check.

## Impact

- **Severity:** high for SLAM vertical accuracy — a single dropout fabricates metres of
  vertical, silently, at high fitness. This is upstream of any %-of-path drift figure
  computed on an affected capture.
- **Frequency:** intermittent (~0.3% of frames here), inherent to the 25 Hz baro vs
  60 Hz hub cadence; more likely the sparser the pressure tag is in a given drain.

## Mitigation (shipped, host-side)

`Mapper._baro_is_outlier` / `[slam] baro_reject_m` (default 50 m, plus a hard reject of
`pressure <= 0`) drops a dropout **before** it reaches the datum or the low-pass filter
(`host/src/roomscan/slam/mapper.py`). Validated: crazySLAM vertical 8.64 → −0.75 m,
path 18.0 → 7.57 m, max step 2.48 m → none >1 m; **no regression** — no clean capture
(`coffeeRoomCircuit{NoMnt,Mnt}`, `roomSweepFull20260730`, `imuTranslationError`) contains
a single sample the guard would reject. This makes the host robust but does **not** fix
the firmware, which still ships a wrong reading on the wire.

## Notes for the firmware fix

- Add a per-channel `have_press` flag to `rs_lsm_sample_t` (`rs_lsm.h`), set only inside
  the `if (shub_acc.press_n != 0)` block (`rs_lsm.c:738-741`) and the non-average branch
  (`rs_lsm.c:391`).
- At the emit site (`vl53l9_app.c:679`), gate the pressure bytes on `have_press`: repeat
  the last good pressure (a small `static float g_last_press_pa;` cache) rather than
  shipping the zero-init 0.0.
- Optional hardening: reject `raw == 0` or `pa` outside ~30000–120000 Pa at the
  conversion (`rs_lsm.c:386`), so a stale SHUB latch can't pass through either.
- On-target validation requires a capture long enough to catch a dropout (intermittent);
  confirm 0-Pa ENV frames disappear over a multi-minute stream.

## Related issues

- BUG-037: the barometer low-pass this dropout drives; the reason a single 44 km spike
  becomes a 2.45 m step rather than a full 44 km jump.
- BUG-082: firmware root cause resolution and host validation defence-in-depth.

## Resolution (2026-08-06)

Resolved by the BUG-082 remediation pass:
- Firmware `rs_lsm.c` now latches complete sensor-hub samples in `g_shub_latch` and sets `out->have_env = 1` ONLY when pressure, magnetometer, and temperature are all valid (`valid_mask == 0x07`). Isolated partial frames with 0.0 Pa pressure are never emitted.
- Host `is_valid_env()` and `SensorState.feed()` validate pressure (30000..120000 Pa), temperature (-40..85 °C), and mag (> 1.0 µT), rejecting any invalid or zero-filled ENV frames host-side as defense in depth.
