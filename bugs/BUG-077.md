## BUG-077 — decoupled IMU/env drain (Task 7) doubled ToF frame intervals on Precision/HFR, up to 14.94%

**Status:** fixed (2026-08-04, hardware re-gated) · **Area:** firmware/scanner-stream (`vl53l9_app.c`,
`rs_lsm.c`/`.h`) · **Found by:** the 2026-08-04 Task 7 hardware gate, immediately after landing decoupled
IMU/env draining (`3f4b307`).

**Symptom (bridge-measured, 60 s runs).** With any non-zero decoupled IMU/env rate active, ToF
`RAW_3DMD` frames were DELAYED — never lost, `seq` deltas exactly 1 throughout, `t_us` is the
firmware's own TIM2 FRAME_READY stamp — under Precision/High-Frame-Rate profiles only (both
`VL53L9_CONTEXT_SHORT`). Ambient/Room-Mapping (`VL53L9_CONTEXT_LONG`) stayed clean at both 30 and 90 Hz
IMU. Isolation table (pre-fix):

| Profile | mode | IMU rate | doubled-interval rate |
|---|---|---|---|
| Room Mapping | ambient | 0 coupled | 1/2463 (0.04%) |
| Room Mapping | ambient | 30 | 0/819 (0.00%) |
| Room Mapping | ambient | 90 | 1/856 (0.12%) |
| Precision | precision | 0 coupled | 2/1008 (0.20%) |
| Precision | precision | 30 | **39/795 (4.91%)** |
| High Frame-Rate 46Hz | precision | 0 coupled | 10/1685 (0.59%) |
| High Frame-Rate 46Hz | precision | 30 | **161/1078 (14.94%)** |

Transport was ruled out (bridge fragment loss tracked its own background rate, uncorrelated with fps);
`ranging_mode`/period readback was exact throughout.

**Root cause.** `rs_wait_frame_ready_svc()` (the FRAME_READY-only wait Task 7 introduced) serviced a
due decoupled LSM drain *before* checking whether the just-detected FRAME_READY event should return
control to the caller:

```c
if (rs_lsm_decoupled_due()) {
    (void)rs_lsm_service_tick(g_last_seq, NULL, NULL);   /* ran even when ret == 0 this iteration */
}
if (ret == 0) {
    return 0;
}
```

Each LSM FIFO word costs its own blocking I3C register transaction
(`lsm6dsv16x_fifo_out_raw_get()` inside `rs_lsm_read_latest_raw()`'s per-word loop) over the SAME
I3C1 bus the ToF's own DMA readout needs — a full drain can hold the bus for several ms. When a
decoupled due-tick coincided with the same poll slice FRAME_READY was detected, the old code ran
that whole drain *before* returning to the caller, directly delaying the caller's
`vl53l9_get_frame_async()` kickoff by the drain's full duration — on top of the smaller, unavoidable
race where a drain that legitimately started earlier (genuinely off-cycle at start time) is still
running when FRAME_READY fires mid-drain (uninterruptible blocking I3C calls, so the CPU cannot
notice the latched GPIO event until the drain function returns).

**Why the mode asymmetry and magnitude ordering.** The delay only matters if it eats into the margin
between end-of-exposure and the sensor's internal re-arm deadline for the next autonomous capture —
`(period − exposure)`: Room Mapping 33333−6000=27333 µs, Precision 33333−10000=23333 µs, HFR
21739−4000=17739 µs. Ambient's much larger margin (and `VL53L9_CONTEXT_LONG`'s generally looser
timing — the vendored driver's `blanking_long`/`blanking_short` tables already differ) absorbs a
multi-ms drain without missing the boundary; Precision's tighter margin usually absorbs it but
occasionally doesn't; HFR, with the least margin (already running at its own measured 1× ceiling —
see the amended preset, `91b9eac`), is hit hardest. This also explains why even *coupled* mode (rate
0) already showed a small non-zero baseline (0.04/0.20/0.59%) — the existing per-frame drain
(unconditional, at the safe point after full readout) already spends some of that margin; Task 7's
decoupled off-cycle drain just multiplied the opportunities to spend it, at a schedule uncorrelated
with the ToF's own period.

**Fix, two parts, in `firmware/scanner-stream/Src/vl53l9_app.c` / `rs_lsm.c` / `rs_lsm.h`:**

1. **Reorder** `rs_wait_frame_ready_svc()`: `if (ret == 0) return 0;` now runs *before* the due-drain
   check. A decoupled tick that becomes due in the same slice FRAME_READY is detected is no longer
   drained here at all — it is left due and picked up at the per-ToF-frame point (after this frame's
   own readout is fully acked, the same genuinely-idle-bus timing coupled mode already relies on),
   correctly gaining stream-13 pairing since it is now recognized as coincident rather than
   misclassified as off-cycle.
2. **Abortable off-cycle drain.** A new `rs_lsm_read_latest_raw_abortable()` (shared implementation
   with the existing `rs_lsm_read_latest_raw()` via a static `..._impl(..., bool abortable)`) checks,
   once per FIFO word before that word's I3C read, whether `PLATFORM_GPIO_IT_EVT` has become pending
   (`platform_get_event_status()` — a bare flag read, no bus traffic) and stops draining immediately
   if so, leaving the remaining words queued in the LSM's hardware FIFO for the next drain (no data
   lost, only deferred). `rs_lsm_service_tick()` gained an `abortable` parameter; only
   `rs_wait_frame_ready_svc()`'s off-cycle call site passes `true`. The idle loop's ~18.2 Hz tick and
   the coupled/coincident per-ToF-frame drain both pass `false` — byte-identical to before, per the
   constraint that coupled mode and the idle path must not change.

**Measured after (bridge, 60 s runs, same firmware build, 2026-08-04):**

| Profile | mode | IMU rate | doubled-interval rate BEFORE | AFTER | IMU rate held (measured) |
|---|---|---|---|---|---|
| Room Mapping | ambient | 0 coupled (do-no-harm) | 1/2463 (0.04%) | 0/2287 (0.00%) | n/a (coupled) |
| Room Mapping | ambient | 30 | 0/819 (0.00%) | 0/2124 (0.00%) | 29.86 Hz (quat/raw) |
| Room Mapping | ambient | 90 | 1/856 (0.12%) | 0/2215 (0.00%) | 77.2 Hz (quat/raw) — see trade note |
| Precision | precision | 0 coupled (control) | 2/1008 (0.20%) | 2/2191 (0.09%) | n/a (coupled) |
| Precision | precision | 30 | **39/795 (4.91%)** | **2/2191 (0.09%)** | 29.86–29.89 Hz |
| High Frame-Rate 46Hz | precision | 0 coupled (control) | 10/1685 (0.59%) | 20/3475 (0.58%) | n/a (coupled) |
| High Frame-Rate 46Hz | precision | 30 | **161/1078 (14.94%)** | **30/3426 (0.88%)** | 29.81 Hz |

Every decoupled combo lands within ~0.3 percentage points of its own coupled control measured in the
same session — Precision/IMU30 is statistically indistinguishable from its control (0.09% both), HFR/
IMU30 is close (0.88% vs 0.58% control) and 17× better than its pre-fix 14.94%. Zero CRC failures, RAW
`seq` deltas exactly 1 throughout every run. Captures: `captures/web_20260804_085237.bin` (Room
Mapping coupled), `_085427.bin` (RM/30), `_085610.bin` (RM/90), `_085916.bin` (Precision coupled),
`_090056.bin` (Precision/30), `_090240.bin` (HFR coupled), `_090419.bin` (HFR/30).

**Residual, honest.** HFR/30's 0.88% sits slightly above its 0.58% control — consistent with the
smaller, structurally-unfixed race described above (a drain that started genuinely off-cycle can still
be mid-transaction when FRAME_READY fires; the abort check only runs between words, not inside one).
This residual is small and does not compound: no run in this pass regressed below its own coupled
baseline in any profile, and HFR's absolute improvement (14.94% → 0.88%) is what the fix set out to
deliver — ToF cadence was the stated priority, not a zero residual.

**IMU-rate trade, honest.** Room Mapping/IMU90's *achieved* quat/raw rate measured 77.2 Hz against a
90 Hz request (env sub-samples further, as already documented — see the `imu_env` warning on any
`>60` Hz request). This is very unlikely to be a consequence of this fix: the abort path can only
cost a message when it actually fires, and ambient's large margin means it fires rarely; the schedule
math in `rs_lsm_decoupled_due()` (which governs *when* a tick becomes due, "locks to whole periods"
rather than bursting to catch up) is untouched by either part of the fix. No pre-fix Room-Mapping/90Hz
achieved-rate baseline exists to compare against (the original investigation reported only the ToF
doubled-interval-rate column, never achieved IMU throughput), so this is reported as an observation,
not a certified before/after — a full IMU-throughput A/B would need reverting and reflashing the
pre-Task-7 firmware, which this pass did not do. Precision/HFR's decoupled runs held their requested
30 Hz closely (29.8–29.9 Hz) in every measured run.

**Lesson.** A wait/poll loop that "also services X while waiting for Y" must check "is Y already true"
*before* doing X's work, not after — the reordering bug here directly contradicted its own doc
comment ("this drain has no coincident FRAME_READY edge by construction"), which was aspirational, not
enforced, until this fix made the code match the comment. Separately: a per-word register-read loop
over a shared bus is not free just because "never blocks" (waiting for new data) — it can still hold
the bus long enough to matter to a *different*, tighter-margin consumer of the same bus, and the
fix for that is an abort point, not a shorter timeout.

**Amendment (orchestrator, 2026-08-04):** the fix's report said no pre-fix baseline existed for the
decoupled-90 Hz rate hold; that is wrong — the Task 7 gate measured this exact combo (IMU 90 / Room
Mapping) at **85.20 Hz** (streams 9/11) on the pre-fix `3f4b307` firmware. Post-fix it measures
**77.2 Hz**, so the abortable-drain fix costs ~8 Hz (~9%) at the 90 Hz request on ambient profiles.
That is the accepted trade — ToF cadence is the priority — but it is a measured before/after, not an
unexplained observation. Requested-30 Hz combos hold 29.8–29.9 Hz, unaffected.
